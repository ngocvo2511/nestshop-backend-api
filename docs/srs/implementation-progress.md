### Delivered behavior and decisions

- `src/modules/auth/` owns AuthModule, controller, DTOs, service, safe response/OpenAPI models, reusable AccessTokenService/AccessTokenGuard and password helper. Three implemented POST routes: `/api/v1/auth/register`, `/auth/login`, `/auth/refresh`. Strict body/query allowlists, no-store responses and existing safe HTTP boundary apply. Registration returns only UserPublic, without automatic login. No production identity-probe, profile, role, logout or password-change APIs were added.
- Normalized unique email at the DTO boundary, explicit active CUSTOMER creation and exact PostgreSQL users_email_key conflict mapping. Passwords follow12–128 Unicode characters, no controls/surrounding whitespace and no normalization. Shared native scrypt retains the existing setup format: N131072/r8/p1, random16-byte salt,64-byte derived key,256MiB maxmem. Admin setup now shares this helper/policy; existing hashes remain compatible. Missing/unsupported password hashes still incur derivation before generic credential rejection. Only explicit public serializers leave AuthService; neither password nor refresh hashes/family records are exposed.
- Added locked `jose@6.2.15`; HS256 access JWTs include verified issuer/audience/sub/role/tokenType/iat/exp and JWT header type. Verifier rejects missing/future/invalid claims and unsupported algorithms/types. Identity derives only from verified claims, with no session lookup. Existing access JWTs remain stateless; newly issued JWTs use current role. Refresh tokens are canonical base64url of32 random bytes, persisted only as SHA-256 with UUID family, status, expiry and consumption/revocation metadata. No schema change/migration needed.
- Login locks the user before verifying its current password/active flag and creating a family. Refresh's initial hash lookup only identifies ownership; the transaction locks user first, then all family token rows in ascending ID, and rereads lifecycle/account state. PostgreSQL clock_timestamp() is read after lock acquisition. One READ COMMITTED manager consumes the old credential before successor insert, satisfying the existing partial unique index. Rolled-back deadlock/serialization codes receive at most two retries; unrelated/unknown failures are not retried.
- Consumed replay returns an outcome from the transaction, commits whole-family REPLAY revocation including successors, and only then throws the HTTP401. LOGOUT/PASSWORD_CHANGE classification takes precedence and preserves prior metadata; expired consumed credentials still retain replay evidence. Expired/unavailable unconsumed credentials cannot rotate. **There is no grace period: the concurrent loser can immediately revoke the winner's replacement.** This is expected baseline behavior, not a second successful rotation.
