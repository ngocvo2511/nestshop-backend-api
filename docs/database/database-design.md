# E-commerce database design

Rendered diagrams: [Conceptual Chen ERD and logical Crow's Foot ERD](README.md).

Proposed implementation specification, 2026-10-29. Based on SRS **v0.9 (2026-10-29)**. This is documentation DDL, not an applied database, migration, or TypeORM implementation.

## 1. Overview and evidence

PostgreSQL 14+, public schema, NestJS/TypeORM modular monolith. Ten P0 tables use UUID keys, explicit foreign keys, integer VND, and timestamptz. No extensions, triggers, additional services, or provider internals are required. All UUIDs are generated by trusted application code. All SQL is wrapped in a transaction for review/reproducibility; do not run it against an existing schema as a migration.

Reviewed sources:

## 2. Scope, assumptions and conflicts

**P0 included:** accounts, single-role RBAC, refresh-family rotation/revocation, role audit, catalog with one image reference, available inventory and manual adjustment audit, direct orders with shipping and item snapshots, status history, VNPay attempts and safe IPN receipt/reconciliation history. Lightweight health has no table.

**Optional P1 retained in requirements, not selected for this baseline:** categories, carts/cart items, notification_deliveries, advanced reporting/history filters. This design assumes no P1 option has been approved; their omission does not remove them from the SRS. No speculative P1 tables or product category FK are emitted. If selected, create a separately reviewed extension: category cardinality/deletion rules, customer cart operations, and notification event keys, PENDING/SENDING/SENT/FAILED states, recipient/template payload, attempts, safe errors, next retry and sending lease all need decisions first. Notification events must then commit with business state; SMTP delivery remains after commit and can duplicate after a crash. Reporting should first use existing orders/items/payments/history rather than an analytics table.

**Deferred/excluded:** address books/default addresses/address CRUD, OAuth, multi-role permission catalogs, refund processing, production payments, taxes/fees/discounts, multi-currency, warehouses, gallery management, carriers, brokers, caches and analytics storage. Avatar remains disabled until selected; no avatar_url field is emitted.

Specific proposed physical decisions:

- One role value per user, no user_roles join table: SRS uses a singular role and old/new-role audit. Account deactivation uses is_active; no hard-deletion API is designed.
- One image_path on products matches SRS section 6 and SEQ-12. A gallery/product_images table is unnecessary until multiple images are required. Path is relative to configured storage root; no image bytes or host paths. SQL rejects common absolute/traversal forms; application filename generation and canonical path containment remain mandatory. File upload and SQL cannot commit atomically; attempt orphan cleanup on SQL failure.
- VND money is bigint, quantities and stock integer. Reject fractional input *before* binding/casting: PostgreSQL numeric-to-integer casts may round. TypeORM/JavaScript must use decimal strings or BigInt for bigint arithmetic/serialization, never unsafe Number conversion. Checked bigint multiplication rejects overflow; service limits must reject it cleanly.
- Proposed field lengths and domestic structured address layout are schema design choices, not settled API requirements. Recipient, phone, address_line, province_city are required; ward/district/postal_code nullable for administrative variation. Validate phone and complete deliverability in DTOs; the database checks required nonblank components. International shipping is unspecified.
- Reject duplicate product IDs at checkout (UNIQUE order_id/product_id); aggregate only if a future API contract explicitly chooses that behavior. No persisted cart is required.
- No separate inventory/reservation/movement table: available stock is the single quantity source. Immutable order_items quantities plus order state represent reservation. A manual inventory audit is distinct and does not log reservations/releases. Initial stock is a create-only input; current available stock is not a permanent initial-stock ledger.
- payment_notifications is the minimal related persistence permitted by SRS 5.7: preserve every safe receipt including repeated, invalid, unknown, late and conflicting observations without overwriting an attempt's canonical result. Reported values are untrusted unless verified; do not label a signed but mismatched amount as an accepted payment. Malformed amounts are NULL plus safe outcome detail. No raw provider JSON, card data, CVVs, tokens or signing credentials.

**Approved target with integration gate:** FR-PAY-005 requires approximately 20-minute local attempt expiry; SRS 5.7 conditions it on verified integration rules and SEQ-25 leaves PENDING when finality is unresolved. Therefore expires_at is a *due-for-policy-evaluation* timestamp, not proof of provider non-charge. No automatic replacement solely because a clock passed. The independent 60-minute order policy is requested here and described throughout the flows, and is approved by the project owner in SRS v0.9 section 9. Both are configurable durations persisted per record. Do not silently resolve either policy by DDL.

## 3. Entity responsibilities and cardinality

| Parent | Children | Cardinality and ownership |
|---|---|---|
| users | refresh_tokens | 1 to 0..many tokens; family_id groups one user's rotation chain |
| users | orders | 1 to 0..many customer purchases |
| users | role_change_audit | Separate actor and affected-user 1 to 0..many links |
| products / users | inventory_adjustment_audit | Each adjustment has exactly one product and one Admin actor |
| orders / products | order_items | Each line belongs to one order and one retained product; order must have 1..many lines at commit (transaction rule) |
| orders / users | order_status_history | Order 1 to 1..many history entries; optional actor means SYSTEM |
| orders | payments | 1 to 0..many attempts; at most one pending and one successful |
| payments | payment_notifications | 1 to 0..many receipts; a receipt may have no known attempt |

All FK IDs are UUID-compatible and use RESTRICT on delete and update. No cascading delete can erase order, payment or audit history. Product deactivation/name/price changes leave snapshots untouched. An account or product referenced by history cannot be hard deleted; deactivate instead. Optional actor/payment links remain NULL only for SYSTEM/unknown-reference cases, never as deletion side effects. A role audit preserves old/new values even after subsequent role changes.

## 5. Constraints, indexes and limits of DDL

The dictionary specifies columns, defaults, checks and PK/FK rules. schema.sql defines all named indexes; database.dbml includes full indexes and comments every PostgreSQL partial index:

| Index / key | Purpose |
|---|---|
| users.email UNIQUE | Normalized email lookup and concurrent registration rejection; lowercase/trim is enforced, semantic email validation is application work |
| refresh_tokens.token_hash UNIQUE | Find one token without plaintext storage |
| refresh_user_family_idx | Revoke/list all user families or one family |
| refresh_one_live_token_idx UNIQUE family_id WHERE ACTIVE and unconsumed | At most one usable rotation successor per family; expiry still checked against time |
| role_audit_target_time_idx / role_audit_actor_idx | Audit by affected user/time or actor |
| product_public_name_idx / product_public_price_idx | Active catalog sorting with ID tie-breaker; no substring-search acceleration is claimed |
| inventory_audit_product_time_idx / inventory_audit_actor_idx | Product audit history and actor FK lookup |
| order_customer_time_idx / order_queue_idx | Own-order pagination and minimal status queue |
| order_due_idx WHERE PENDING_PAYMENT | Startup/periodic reservation expiration candidates |
| UNIQUE order_items(order_id, product_id) / item_product_idx | Distinct lines, order detail and product FK lookup |
| history_order_time_idx / history_actor_idx | Ordered history and actor lookup |
| history_one_initial_idx UNIQUE order_id WHERE previous_status IS NULL | At most one creation history row |
| payment_order_time_idx | Attempt history and order FK lookup |
| payment_one_pending_idx / payment_one_success_idx UNIQUE order_id | Separate partial predicates PENDING / SUCCESS; neither creates an unconditional one-payment-per-order rule |
| payment_due_idx WHERE PENDING | Attempt evaluation candidates |
| notification_payment_time_idx / notification_outcome_time_idx / notification_correlation_idx | Attempt receipts, reconciliation queue and request correlation |

Ordinary PostgreSQL UNIQUE allows multiple NULLs; no nullable key is used for settlement idempotency. Receipt transaction references are deliberately not unique because duplicate receipts must be retained. Provider reference on payments is globally unique for the single Sandbox merchant/environment deployment. Multi-merchant/environment sharing would require a redesigned uniqueness scope. Provider transaction reference uniqueness is not asserted without verified provider guarantees.

**SQL enforced:** allowed canonical statuses, positive money/quantity, nonnegative available stock, signed nonzero manual deltas with previous+delta=new, required adjustment reason, unique email/hash/order-product/reference, FK retention, expiry-after-creation, coherent token revocation metadata, payment terminal timestamp, valid history edges, and one pending/success attempt. line_total_vnd is generated in SQL; omit it on INSERT/UPDATE. Its positive operands are non-null, so its value is always present for valid rows even though the generated column is not explicitly NOT NULL.

**Transaction enforced (not falsely claimed as CHECKs):** at least one line and one initial history per committed order; total_vnd = SUM(line_total_vnd); payment amount = order total; family UUID has one immutable owner; legitimate status transitions and verified settlement authority; audit/history insertion matches the actual mutation; immutable shipping/item/history/audit/receipt data; and reservation release exactly once. Cross-row sums or provider verification cannot be expressed safely as a simple row CHECK. No triggers or SECURITY DEFINER functions are introduced. Use narrowly allowlisted repository operations and restricted database credentials; arbitrary direct SQL can violate these transaction-only rules. updated_at must be set explicitly by the service/TypeORM on updates; DEFAULT now() only handles inserts.

## 6. Transactions, concurrency and business invariants

Use PostgreSQL READ COMMITTED with explicit row locks and conditional writes. Recheck current state/deadlines after obtaining locks. Retry deadlocks/serialization conflicts with bounded retries and safe responses; never retry provider side effects blindly. All statements in a flow use the same TypeORM transaction manager. Candidate scans confer no authority until locked recheck. Use wall-clock database time after locks (for example clock_timestamp()), not a stale transaction-start now(), when judging deadlines after contention.

### Authentication, roles and password changes

Store a secure salted password hash; hash high-entropy refresh token bytes with SHA-256 and store only 64 hex characters. A family UUID is created at login and copied on every replacement; no separate session table is necessary. For login, refresh, logout and password change, lock the owning users row first, then relevant token rows in deterministic ID order. Re-read active-account/password/session state under that lock. This intentionally serializes refresh across the user's devices and provides a stable family lock even when a new token is inserted. Never lock a token and then its user; a hash lookup may identify the owner without taking a token lock first.

Rotation requires status ACTIVE, consumed_at NULL, expires_at > current time and an unrevoked family. Set the old consumed_at before inserting its successor to satisfy the partial unique index, in one transaction. A consumed token may retain status ACTIVE as the SRS permits; it is never usable again. An ACTIVE consumed row is replay evidence, not a second active credential. If a consumed row is replayed, revoke every family row (including successor) with REPLAY; commit revocation even though the HTTP response is rejection. Throwing inside a transaction that rolls back revocation is incorrect.

LOGOUT/PASSWORD_CHANGE revocation takes precedence over replay classification; retain consumed_at while setting status REVOKED, revoked_at and distinct reason across the family. Repeated revocation must preserve prior ordinary-revocation classification. Expired unconsumed tokens fail without rotation; expire them lazily/periodically if desired. All rotation checks must follow the documented replay/ordinary-revocation policy; do not erase consumed evidence by expiring it early. Retention/purge policy must preserve evidence through the family's security window. A loser in concurrent rotation may revoke the winning replacement as replay, as required by SRS; no grace period is designed.

Password change updates password_hash and revokes *all* families in the same user-locked transaction. Login must participate in that lock so it cannot insert a family based on a password verified before the change. Access JWTs remain stateless until expiry. Role change locks affected user and writes role plus role_change_audit atomically; verify actor Admin authority. Changed role claims on existing access JWTs may remain stale until token expiry; immediate privilege removal is an unresolved policy, not a new token-version mechanism.

### Checkout, stock adjustment and order history

Checkout validates nonempty distinct product IDs/positive integer quantities and shipping fields, locks products in ascending UUID order, reloads active flags/prices/stock, computes exact VND totals, then decrements stock conditionally (`stock_available >= requested_quantity`). Require one affected row per product. Insert order, immutable lines and initial SYSTEM history in the same transaction. Capture one creation instant and set reservation_expires_at = creation + configured 60 minutes. Any failure rolls back *all* deductions and records. Snapshot product name/unit price and all shipping fields; later product/profile changes never rewrite them. Reject overflow and invalid input before issuing persistence operations.

Admin adjustment locks the same product row, reads previous available stock, adds the signed delta safely in bigint, validates integer range and nonnegative outcome, writes product plus audit atomically. No zero-delta audit noise; no general catalog-update path may write stock. Available stock can increase due to manual restock or released reservation; it is not total physical stock including reserved units.

Reservations have no additional quantity copy: PENDING_PAYMENT + immutable lines means reserved; PAID/PROCESSING/SHIPPED/COMPLETED means consumed; CANCELLED/EXPIRED means released. Fulfillment writes order + next-edge history atomically; only PAID→PROCESSING→SHIPPED→COMPLETED. Customer cancellation only PENDING_PAYMENT, owned, before reservation deadline. History records authenticated actor for customer/staff/admin actions and NULL for SYSTEM/payment/scheduler. Initial previous_status is NULL; no same-state history on a duplicate/no-op.

### Payment initiation and IPN idempotency

Every existing-order payment/cancel/expiry/fulfillment mutation locks **order first, then payments by ID, then products by ascending ID if releasing**. Checkout has no preexisting order to lock and only acquires products in ascending order; never lock products before an existing order in another flow. This common order serializes settlement with cancellation and expiration.

Initiation verifies ownership, PENDING_PAYMENT, current time before reservation_expires_at, and all prior attempts genuinely FAILED/EXPIRED. Reuse a PENDING URL only if provider rules establish safety; otherwise return conflict. Never terminate an attempt just to create another. Generate a unique provider_reference and signed URL locally, persist amount from order total, set expires_at = attempt creation + configured approximately 20 minutes, and commit one PENDING row. Signing failure produces no attempt. The order can expire before an attempt's 20-minute timestamp if initiated late; order eligibility is always checked independently. Signed URLs contain no signing secret but are sensitive and must not enter logs or public listings.

For IPN, validate official signature/format before trusting provider input; resolve reference, lock order then attempt and revalidate all applicable data (merchant/environment, amount conversion, VND, transaction fields and result codes). Known/unknown/invalid receipts store only bounded safe normalized observations. A verified signature alone is insufficient. No browser return updates payments/orders/stock.

A valid applicable success requires order PENDING_PAYMENT and before reservation expiry, current attempt PENDING and eligible under the confirmed attempt-deadline policy; set SUCCESS + terminal_at, order PAID + history, and SETTLED receipt in one transaction. Do not deduct stock again. A verified applicable failure sets FAILED + terminal_at and a FAILED receipt, retaining order and reservation. Store canonical provider transaction/reference/result fields on the attempt only for the accepted terminal result. On database failure, do not acknowledge a result as durably handled; provider retry must safely reprocess it.

Duplicate successful callback observes committed SUCCESS/paid state and appends DUPLICATE without a second history row or business effect. Duplicate failure behaves likewise. Concurrent callbacks serialize on order; partial unique success index provides a second guard. A deduplication hash or receipt-unique key is unnecessary for P0 business idempotency: multiple observations may be retained while conditional state transitions happen once. Result changes for a terminal attempt are CONFLICT/LATE, never another terminal transition. An old failed/expired attempt cannot settle even if its signed late result reports a real charge. Keep its receipt and do not overwrite canonical state. Unknown references have NULL payment_id and UNKNOWN_REFERENCE; invalid signatures use INVALID, with reported fields treated as untrusted. Correlation UUIDs allow safe diagnostics; limits/rate controls are implementation work.

### Expiry, release and reconciliation

Startup plus periodic scans evaluate PENDING attempts by expires_at and pending orders by reservation_expires_at. The interval is configuration still to be chosen. For due attempts, apply the verified expiry/finality policy, then lock order→attempt and recheck. When safe, set attempt EXPIRED and terminal_at only; no stock/order/history change. If policy is unresolved, keep it pending and block replacement. Elapsed local time does not establish the provider did not charge.

For due unpaid orders, lock order→attempts→products, recheck deadline and status, conditionally transition PENDING_PAYMENT→EXPIRED, expire remaining PENDING attempts with terminal_at, restore each line quantity, and insert SYSTEM history in one transaction. Customer cancellation performs the analogous CANCELLED transaction. Only the transaction that actually changes the pending order restores stock; zero affected rows means no release. Overflow on stock restoration aborts the transaction and requires investigation, never silent clipping. Payment success and stock adjustments share locks with these paths; no lost updates, negative stock or double release is possible *when this protocol is followed*.

An IPN after cancellation/order expiry never reactivates or changes stock and remains a LATE/CONFLICT receipt for read-only Admin reconciliation. At the attempt deadline, an unresolved PENDING attempt is not automatically settleable merely because it is still marked PENDING: deadline applicability must be checked against the integration policy. Exact provider semantics are a release blocker. Reconciliation uses receipts joined to attempts/orders, without a mutable reconciliation status duplicated onto the order. This MVP records inspection outcomes, not a manual settlement/refund workflow; any future annotations/resolution need an auditable extension. Rejected or late receipts may be recorded even when a business mutation is rejected; do not accidentally roll those diagnostic writes back with an expected HTTP rejection.
